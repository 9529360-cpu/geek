# Hello-GPT 1.4.48 安装包静态审计（2026-09-13）

> 样本是用户提供的 `Hello-GPT_1.4.48_x64.exe`，仅作外部产品研究。
>
> 它不是 Geek 的依赖、构建输入或发布物；本记录也不把它等同于任何公开仓库的官方构建。

| 项目 | 结果 |

| 安装器线索 | Nullsoft Install System v3.04；请求 `asInvoker` |

GitHub 普通 Git 会阻止超过 100 MiB 的单文件；本样本不应直接写进 Git 历史。仓库当前没有 `.gitattributes`/Git LFS 规则，因此不能只提交一个没有实际 LFS 对象的 pointer。

## 当前能证明什么

- 外层安装器具备典型 NSIS 的文件、注册表、Shell 与进程管理 imports；这些属于安装器能力，**不能**推断被安装应用拥有相同能力。
- 样本中能识别到 `Hello-GPT`、`2026 Hello-GPT`、NSIS 完整性校验文本，以及一个嵌入 CAB 和一个 gzip 数据段。
- 仅凭外层静态信息，不能可靠识别内层技术栈、网络端点、权限模型、账号隔离、消息发送行为或许可证；也不能证明它与公开 Hello-GPT/GPT Academic 仓库为同一来源。

公开的 `fayujiang/Hello-GPT` 项目说明其定位是多模型、文档/论文处理、插件与知识库能力；它可作为产品信息架构的远期研究材料，但不构成这个二进制的来源证明。

## 对 Geek 的产品判断

当前样本没有提供足够的、可验证的功能行为，**不应据此直接修改 Geek 的群发、WebView、IPC 或账号安全实现**。尤其不能为了模仿第三方安装包而降低：

- WebView sandbox、context isolation 或 webSecurity；
- 账号独立 partition 与 IPC owner 校验；
- 群发的账号/Job/附件 owner 绑定；
- 正式客户端发布的完整性与回滚流程。

最直接且有价值的改进方向是让 Geek 自己的发布物更容易被用户验证：

1. 继续维持 installer、`latest.yml`、blockmap 与版本发布顺序的一致性校验；
2. 在发布文档中提供面向用户的校验摘要/命令；
3. 将 Windows Authenticode 证书与签名自动化作为单独的运营决策：它需要证书与 Secrets，不能因本次研究自行引入或发布。

这与当前仓库发布安全规则一致；本样本“未发现签名表”只能说明第三方样本的信任信息不足，不能代替 Geek 自身签名方案的验收。

## 若继续研究

1. 在隔离、无网络、无真实用户数据的 Windows 分析环境中解开 NSIS payload，绝不执行其安装器或内层程序。
2. 对解出的文件逐个记录 SHA-256、版本资源、签名和依赖清单；先建立材料清单，再讨论行为。
3. 只把已验证的用户流程映射到 Geek 当前 active caller；每个候选能力独立提出“用户场景 → authoritative owner → 安全边界 → 验证计划”。
4. 原始样本如需长期共享，应由仓库所有者明确选择 Git LFS 或受控 GitHub Release 附件；上传前再次核对 SHA-256 与来源许可。
