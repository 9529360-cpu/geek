# 群发体验与账号级任务改造

> 对应 Issue #165。本文是 `ux/broadcast-account-jobs` 分支的产品与实现约束。先固定行为与文案，再按本文改运行时代码；不把历史 UI 原型当作当前实现来源。

## 1. 这轮为什么要改

当前群发已经具备多平台发送、附件、联系人/群组选择、定时、保存消息、失败导出等能力，但编辑态、运行态和账号归属态混在 `ui/app.js` 的窗口级变量里。当前全屏 overlay 又让“编辑群发”和“群发任务正在执行”成为同一个页面状态，造成两个问题：

1. 用户一旦开始发送，原账号聊天页面被遮住，必须停留在群发页面等待；
2. 如果以后仅把发送界面隐藏而不先修任务模型，`activeId`、全局运行变量、附件/选择状态和历史回写可能发生归属漂移。

这轮先把“任务是谁的”做正确，再把发送中/发送完成体验变轻。

## 2. 核心模型：Broadcast Job

已经点击开始并成功创建的群发，不再理解为“当前窗口正在群发”，而是一个明确属于某个账号的任务。

任务创建时冻结至少这些信息：

- `accountId`
- `partition`
- 目标 WebView / guest 身份
- 收件人 targets
- 消息正文
- 附件 token / 元数据
- 必要发送选项（例如 @全体、名片等）
- 发送间隔
- 创建时间
- 运行状态、成功数、失败数、当前进度、失败明细

硬规则：

- 任务创建后，发送循环不再使用之后的 `activeId` 决定发送账号。
- 切换账号只影响“当前显示哪个账号页面”，不改变任务执行账号。
- `sendHistory` 必须回写 `job.accountId` 对应账号沙箱。
- 定时任务必须保存明确的 `accountId`；触发时不得使用当时正在查看的账号。
- 第一版只允许一个活动 Broadcast Job，不在本轮扩展多账号并发群发。

## 3. 账号页内任务条

任务条不是全局 Toast，也不跟随用户切换账号。

例：用户在账号 A 创建群发。

- 开始发送后，群发 overlay 关闭，恢复账号 A 的聊天页面。
- 账号 A 页面右上角显示任务条。
- 用户切换到账号 B，账号 A 的任务仍继续，但任务条隐藏。
- 用户切回账号 A，任务条重新显示当前实时状态。
- 完成后任务条留在账号 A 页面，直到用户手动关闭。

可见性规则：

`activeId === job.accountId`

此规则只控制 UI 是否展示；任务执行不得依赖 `activeId`。

### 3.1 任务条文案

发送中：

- 主文案：`正在群发 18 / 52`
- 辅助信息：`成功 17 · 失败 0`
- 等待间隔时：`下一条 8 秒后`
- 操作：`暂停`、`停止`

暂停：

- 主文案：`群发已暂停 18 / 52`
- 操作：`继续`、`停止`

完成（全部成功）：

- 主文案：`群发完成 · 52 / 52`
- 辅助信息：`全部发送成功`
- 操作：`×`

完成（部分失败）：

- 主文案：`群发完成 · 成功 49 · 失败 3`
- 操作：`查看失败`、`×`

停止：

- 主文案：`群发已停止 · 成功 18 · 未发送 34`
- 操作：`×`

不自动显示大弹窗；失败详情按需展开/导出。

## 4. 群发编辑窗口：本轮保留主体，不推倒重做

当前目标选择、保存消息、附件、多平台发送等链路已经成熟。本轮保留现有群发编辑弹窗整体框架，只修明显不符合操作语义的地方。

### 4.1 发送按钮与摘要

旧：

- `发送前请确认对象与间隔`
- `开始群发`

新：

- 主按钮根据选择实时显示：`发送给 52 个聊天`
- 按钮左侧摘要：`1 条消息 · 2 个附件 · 间隔 5–10 秒`
- 没有收件人时按钮禁用或保持 `请选择发送对象`

不再增加二次确认弹窗。

### 4.2 附件

当前“添加图片/视频/文件”使用 switch，但实际行为是一次性打开文件选择器，选完又自动关闭 switch。这不是开关语义。

改为按钮：

- `＋ 添加附件`
- 已选择后显示文件列表 / chip

真实附件安全边界保持不变：最多 10 个、单文件 512 MiB、单次选择总计 1 GiB。界面不得继续显示旧的“最大100MB”。

### 4.3 电子名片

当前“添加电子名片”也使用 switch，但实际行为是打开联系人选择器。

改为按钮：

- `＋ 添加电子名片`

`@全体群成员`继续保留为真正的开关/复选项。

### 4.4 发送对象

主路径只强调：

- `选择联系人或群组…`

选择器内部继续提供：

- `全选`
- `联系人`
- `群组`
- `清空`

“更多发送方式”保留：

- 粘贴联系人号码
- CSV/TXT 联系人文件
- 向所选群组成员私聊发送
- 同一标签下的所有联系人

“所有联系人 / 所有群组 / 所有人”不再需要作为视觉上强势的独立主模式；如果本轮改动成本会影响既有选择逻辑，可以先保留内部行为，但在 UI 上降级为快捷选择。

### 4.5 排除项

`排除联系人 / 排除群组`不是“发送方式”，而是发送范围过滤条件。

目标文案：

- 默认不展开；
- 有排除项时显示：`已排除 3 个对象`；
- 点击后再管理联系人/群组排除列表。

本轮若结构移动会扩大 DOM 与逻辑改动，可先保持底层数据结构不变，但文案与入口必须从“发送方式”降级为过滤项语义。

### 4.6 群组集合（原“保存群组标签”）

当前“保存 / 全部群组 / 标签”并列，用户不容易理解“保存什么”和“全部群组”其实是清除筛选。

统一称为：`群组集合`

文案：

- `保存当前选择`
- 已保存集合显示：`马来客户 12`
- 当前筛选状态：`群组集合：马来客户 ×`
- 删除：`删除群组集合「马来客户」？不会删除真实群组。`

保存成功不再 `alert()`；使用页面内轻提示。

### 4.7 系统 alert / prompt / confirm

群发高频流程尽量不再被系统弹窗打断。

本轮优先取消：

- 保存群组集合后的成功 `alert`
- 群发完成失败明细的大 `alert`

保存名称改为原地小输入框属于优雅方向；如果本轮为避免扩大改动暂时保留 `prompt`，必须至少取消成功后的第二次 `alert`。

真正破坏性操作（删除保存内容）可继续有确认，但后续应统一为应用内确认样式。

## 5. 定时发送

现在“单条定时发送”和“多消息定时任务管理”混在同一个主流程里，人的心智不清晰。

最终产品方向：

- 普通群发只保留 `立即发送 / 定时发送`；
- 选择定时发送后，只显示一个日期时间；
- 多条定时任务属于独立“定时任务管理”能力，不应长期堆在单次群发编辑主流程里。

但本轮首先修正确性：

- 每个定时任务固化 `accountId`；
- 触发时使用该账号，不使用当前 `activeId`；
- 已有持久数据需要兼容：旧任务缺少 accountId 时只能在其所属账号沙箱内补齐/解释，不允许跨账号猜测。

多定时任务 UI 的彻底拆分列为第二阶段，不与账号级 Job 改造混成一次大重写。

## 6. 消息编辑与变量

当前内部语法 `%nc`、`%nr`、`%sa`、`{A|B|C}` 可以继续保留，避免影响成熟发送解析。

本轮文案原则：

- 用户优先看到“联系人/群组名称”“用户真实昵称”“问候语”，不要求理解内部占位符。
- placeholder 不再把 `%nc` 当主要教学内容。

建议新 placeholder：

`输入要发送的消息，可用下方变量插入联系人名称或问候语`

多版本消息的可视化编辑（版本 1 / 版本 2 / ＋添加版本）列为第二阶段。

## 7. 发送间隔

当前 5–10 秒双滑块继续保留底层能力。

本轮文案：

- `发送间隔`
- `5–10 秒 · 随机等待`

未来方向：默认折叠为“推荐 / 更稳妥 / 自定义”，但不在本轮重做发送节奏算法。

## 8. 打开、运行、再次打开群发的行为

### 无活动任务

点击群发：正常打开编辑窗口。

### 有活动任务，且属于当前账号

点击群发：不得重新初始化正在运行任务的变量、附件、targets、暂停/停止状态。

优先行为：聚焦/显示当前账号任务条，不重新打开一个会覆盖运行态的编辑器。

### 有活动任务，但属于其他账号

当前账号第一版不允许再启动第二个并发任务。点击群发时给出轻提示：

`另一个账号正在群发，请等待任务完成后再开始新的群发。`

任务条仍只在所属账号页面可见。

## 9. 完成后的行为

不再回到一个占满页面的“发送完成页”。

- overlay 在任务创建成功后已经关闭；
- 完成状态只更新账号页右上角任务条；
- 全成功：用户关闭即可；
- 有失败：可查看失败项 / 导出失败名单；
- 失败结果与历史归属原账号。

## 10. 本轮必须完成

1. 账号级 Broadcast Job，运行态不再依赖窗口级 `broadcastRunning / broadcastStop / broadcastPaused / broadcastCurrent / broadcastOkCount` 等全局变量决定任务执行。
2. 任务固定账号 / partition / WebView / targets / message / files / interval / 必要发送选项。
3. `sendHistory` 显式写回任务账号。
4. 定时任务显式绑定账号。
5. 开始发送后关闭 overlay，恢复原账号聊天页。
6. 账号页右上角任务条；切账号隐藏，切回恢复。
7. 运行中再次点击群发不得重置任务。
8. 完成不再弹失败大 `alert`。
9. 附件与电子名片改成动作按钮语义；`@全体`保留开关。
10. 修正文案：附件真实限制、消息 placeholder、按钮摘要、群组集合等。
11. 新增聚焦 contract，覆盖账号 owner、历史 owner、定时 owner、任务条可见性和重复打开保护。

## 11. 第二阶段，不在本轮扩大

- 多账号并发群发。
- 独立“定时任务管理”页面/入口。
- 变量 token 可视化编辑器。
- 多版本消息可视化编辑器。
- 完整应用级 Dialog / Toast 基础设施。
- 发送间隔“推荐 / 更稳妥 / 自定义”预设系统。
- 群发历史完整管理中心。

## 12. 不改安全与发送边界

本轮不得改变：

- WA/TG/LINE transport 的发送语义；
- `GeekBroadcastSafety` 的目标聊天与 composer 校验；
- 附件 opaque token 边界及主进程真实路径隔离；
- 10 文件 / 512 MiB 单文件 / 1 GiB 单次选择 / CSV-TXT 5 MiB 等安全限制；
- WebView sandbox / nodeIntegration / contextIsolation / webSecurity；
- 支付、翻译、订阅、Cloudflare、updater；
- `package.json.version` 和 `.github/release-client-version`。

## 13. 验收路径

至少验证：

1. 账号 A 创建群发 → overlay 关闭 → A 页面右上角显示任务条。
2. 切 B → A 任务继续，B 不显示 A 任务条。
3. 切回 A → 进度继续显示。
4. A 的发送全部使用 A 的 WebView / partition。
5. A 的 `sendHistory` 只写 A。
6. 定时任务在 B 页面可见时触发，仍使用创建任务的 A。
7. 运行中再次点击群发不重置任务、不串附件、不串 targets。
8. 完成后无大完成页、无失败大 alert；失败可查看/导出。
9. 现有广播安全、LINE 图片、Telegram 原生附件、附件 token、CSV/TXT 导入、UI untrusted DOM contracts 全部继续通过。
10. 新增群发账号级任务 contract 通过，标准 PR CI 全绿后再讨论合并。
