# Geek：个人中心与应用实例右键菜单——功能边界与实施任务

> 本文是给后续实现者的产品定义和施工边界。先读源码，再动手；不得凭文件名或提交记录猜架构。

## 一、目标：三个相关但不同的功能

### A. 登录前个人中心信息

极客账户登录后、进入应用主界面前，已有一个登录/个人中心环节，会显示与极客账户相关的信息，例如：

- 邮箱账户
- 字符/额度/字符余额等账户信息
- 其他与极客账户订阅或使用权相关的信息

这是一项独立功能，不等同于应用设置，也不等同于导航栏中某个 WhatsApp/Telegram 实例的操作菜单。

要求：

- 保留现有登录前流程和已验证行为，不重写登录流程。
- 找到现有字符/账户信息的真实来源、API/IPC 调用链和显示位置。
- 将它整理为清晰的“个人中心/极客账户”信息入口或面板，位置应由现有应用结构决定；不得凭空新增重复的登录页或第二套账户状态。
- 邮箱、字符等信息只显示真实读取结果；加载失败必须明确显示失败状态，不得伪造默认余额或成功状态。
- 不在客户端新增保存供应商密钥、翻译服务器地址或其他敏感凭据的逻辑。

#### 2026-08-31 产品补充：应用设置内只读个人中心

阿豪确认：主界面的“设置”可视为“应用设置”，其中允许增加一个只读“个人中心”卡片，仅展示：

- 极客账户邮箱
- 剩余字符

该卡片不是第二套账户中心或账户状态 owner。它必须直接复用现有 subscription.getState()/refresh() 数据源，不新增登录、账户缓存、余额计算、保存或修改账户动作。登录前/进入主界面前的现有个人中心流程继续保留。若账户信息或余额无法可信读取，应用设置内必须显示“未知/暂不可用”，不得以 MAX_SAFE_INTEGER、假 0 或其他默认值代替。


### B. 应用实例/账号的右键菜单

导航栏中的每个应用项代表一个具体应用实例/账号。用户右击该项时，应出现只针对当前实例的上下文菜单，例如：

- 设置代理
- 刷新应用
- 重新登录/扫码登录（如果现有适配器支持）
- 重命名（如果当前产品已有账号名模型）
- 删除账号（沿用现有安全删除和清理流程）

第一阶段至少实现并验证“设置代理”和“刷新应用”，其他菜单项只能在现有调用链明确支持时加入。

硬性要求：

- 菜单必须绑定被右击的具体实例 ID，而不是当前选中项的模糊全局状态。
- 右击 WhatsApp 后操作 WhatsApp；右击其他平台后不能误操作 WhatsApp。
- 设置代理必须沿用现有账号数据边界、代理协议校验和持久化流程。
- 刷新应用只能刷新目标实例，不得重建或刷新其他 WebView。
- 不新建一个与实例右键菜单竞争所有权的账户中心入口。
- 不把应用实例操作塞进全局设置页面。

### C. 迁移原有“设置 > 账号设置”中的实例级功能

现有“设置”页面中的“账号设置”包含两类内容，必须先逐项盘点：

1. **应用/全局级设置**：继续留在设置页面。
2. **具体账号/应用实例级设置**：迁移到导航栏对应账号项的右键菜单或其子菜单。

不得整块粗暴搬走。必须建立迁移表：

| 现有设置项 | 实际作用范围 | 新入口 | 是否保留旧入口 | 验收证据 |
|---|---|---|---|---|
| 逐项填写 | 全局 / 平台 / 实例 | 设置页 / 右键菜单 | 保留 / 移除 / 兼容跳转 | 测试或真实点击记录 |

迁移完成后：

- 全局应用设置仍然可用。
- 实例级设置从目标账号右键进入。
- 同一个功能不得出现两个互相独立、状态来源不同的实现。
- 如果为兼容保留旧入口，旧入口必须调用同一个 canonical handler，不得复制逻辑。

## 二、绝对禁止

- 不得把以上三个功能合并成一个模糊的“Account Center”页面。
- 不得新增主导航入口来替代现有应用项右键菜单。
- 不得先写 UI 再猜 IPC、preload、store 和适配器。
- 不得直接在 master 上试验。
- 不得删除或回退现有稳定功能。
- 不得修改设置、导航、账号存储、WebView partition 或登录恢复边界，除非先在审计文档中证明必要。
- 不得仅凭单元测试通过宣布完成；必须做 renderer → preload → IPC → service/store → WebView/适配器的真实链路验证。

## 三、施工顺序

### Phase 0：只读审计，禁止改代码

先检查当前 `origin/master`，输出：

1. 导航栏应用项的创建位置和实例 ID 来源。
2. 现有右键菜单的创建者、所有权和事件流。
3. 现有设置页“账号设置”的每个字段及真实调用链。
4. 极客账户登录、邮箱、字符信息的真实 API/IPC/缓存来源。
5. 代理设置、刷新应用、重新登录、删除账号的现有入口。
6. account-data-boundary、account-data-store、account-reference 之间的关系。
7. renderer、preload、main、service 之间哪些文件必须改，哪些明确不能改。
8. 一份“功能存在/已接通/已验证/未知”的能力表。

Phase 0 只允许新增审计文档，不允许修改产品代码。

### Phase 1：先写契约和测试

为以下行为写失败测试或契约测试：

- 当前实例右键菜单目标绑定。
- 跨平台/多账号不会串操作。
- 设置代理的账号范围和持久化。
- 刷新只作用于目标实例。
- 全局设置和实例设置分类正确。
- 旧账号数据可迁移且不丢失。
- 邮箱/字符信息加载成功、空值、过期和失败状态。
- 敏感信息不出现在日志和错误正文。

### Phase 2：最小实现

优先只实现：

1. 个人中心信息的真实读取和展示。
2. 已有导航栏应用项的右键菜单壳。
3. “设置代理”接入现有 canonical handler。
4. “刷新应用”接入现有 canonical handler。
5. 按迁移表逐项迁移实例级设置。

### Phase 3：真实验收

必须在 Windows 实际启动应用并验证：

- 极客登录后能看到正确邮箱和字符信息。
- 信息加载失败时没有假数据。
- 右击 WhatsApp，设置代理只影响 WhatsApp。
- 右击另一个实例，刷新只刷新另一个实例。
- 多账号切换后菜单目标不串号。
- 重启应用后账号、设置和菜单仍然正常。
- 全局设置没有被错误移除。
- 旧账号数据、登录状态和 WebView partition 不被破坏。

## 四、交付格式

实现者必须提交：

- 审计文档
- 迁移表
- 变更文件清单及每个文件的理由
- 测试命令和真实输出
- Windows 真实点击验收记录
- 未完成项和已知风险
- 独立 review 结论

“代码存在”“测试通过”“应用能启动”都不等于功能完成。

# 给网页版 GPT 的执行提示词

你现在负责实现 `9529360-cpu/geek` 仓库中的“个人中心 + 应用实例右键菜单 + 账号设置迁移”。不要凭感觉设计，不要直接改 master，不要把需求简化成一个 Account Center 页面。

请严格按以下顺序执行：

1. 以当前 `origin/master` 稳定线为基线，建立独立 worktree/分支；先检查工作区，不覆盖已有未跟踪文件。
2. 第一轮只读源码审计，禁止修改产品代码。完整阅读导航栏应用项、右键菜单、设置页账号设置、account-data-boundary、account-data-store、account-reference、preload、main 和对应适配器。输出调用链和“全局设置 vs 实例设置”迁移表。
3. 明确区分三个功能：
   - 极客账户个人中心：登录后显示真实邮箱、字符/额度等信息；
   - 导航栏应用实例右键菜单：针对被右击的具体 WhatsApp/Telegram/Facebook 实例；
   - 现有设置中属于具体实例的账号设置迁移到右键菜单。
4. 不新增与现有导航竞争的主入口，不重写登录流程，不复制账号状态，不把应用设置整体搬走。全局/应用级设置继续留在设置页；只有实例级项目迁移。
5. 先写失败测试/契约，再实现最小垂直切片。至少验证：实例 ID 绑定、跨账号不串操作、代理设置持久化、刷新只刷新目标实例、个人中心真实数据及失败态、旧数据迁移、敏感日志不泄漏。
6. 所有实现必须沿用现有 renderer → preload → IPC → service/store → adapter/WebView 调用链。若发现需要改变边界，先停止并报告，不要自行发明第二套状态源。
7. 每个阶段都记录实际命令、输出、修改文件和证据。单元测试通过不算完成，必须在 Windows 真实启动并点击验收：登录、个人中心邮箱/字符、右击 WhatsApp、右击其他实例、代理、刷新、重启恢复。
8. 在提交前做只读审查：检查是否误改设置全局行为、主导航、登录恢复、WebView partition、账号存储；检查是否遗留重复入口、死监听器、旧 API 绕过新契约或敏感日志。
9. 最终只提交独立分支，不合并 master。最后报告：分支名、提交、变更文件、测试输出、真实验收结果、未完成项和风险。任何没有真实验证的项目必须标记为 unknown，不得声称完成。
