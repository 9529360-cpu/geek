# 群发附件回归修复契约（2026-08-28）

> 适用于 Issue #165 / Draft PR #166 `ux/broadcast-account-jobs`。本契约只修复当前账号级 Job Runtime 对成熟群发能力造成的回归，不恢复已被真实客户端否决的旧产品化分支，也不改变发布版本。

## 目标与边界

- `BR-ATT-001`：即时群发继续使用现有 opaque short token 和既有 WA/TG/LINE transport，不向 renderer 暴露真实路径。
- `BR-ATT-002`：WhatsApp 多附件按原语义逐个发送，正文只放在最后一个附件 caption。
- `BR-ATT-003`：单个附件失败时只能重试该附件；已经确认成功的附件不得因为后续附件失败而再次发送。
- `BR-ATT-004`：附件与电子名片可以组合；附件全部成功后名片发送一次。仅电子名片也属于有效群发内容。
- `BR-ATT-005`：Telegram 原生附件批次、LINE/其他平台的文件注入事务不得在结果不明确时整体自动重放。
- `BR-JOB-001`：即时 Job 在账号/WebView/transport 初始化失败时必须进入 `failed` 终态并释放同账号执行槽，不能永久停留在 `running`。
- `BR-JOB-002`：scheduled/queued Job 的账号页面暂未就绪仍沿用既有有界恢复机制，不因即时 Job 修复而提前终止。
- `BR-DRAFT-001`：群发编辑器绑定打开时的账号；编辑期间若当前账号改变，发送必须 fail closed，要求重新打开编辑器。
- `BR-DRAFT-002`：Excel 号码、电子名片和附件草稿在新编辑会话开始/成功消费后清空，不得串入另一账号。
- `BR-TARGET-001`：同一 Job 的规范 chatId 必须去重，号码、群成员 LID→PN 等入口不得让同一收件人重复发送。

## 非目标

- 本轮不更改账号级并发、同账号单 executing Job、随机间隔和定时附件 durable ref 设计。
- 本轮不修改 `package.json.version`、`.github/release-client-version`，不发布客户端。
- 客户备注是后续独立数据与 UI 能力；它不得阻塞本次附件回归修复，也不得未经明确设计进入外发正文。

## 确定性验收

| 验收 ID | 对应需求 | 判定条件 |
|---|---|---|
| `AT-ATT-001` | `BR-ATT-002/003` | 三个 WA 附件中第二个首次失败：第一个调用 1 次，第二个调用 2 次，第三个调用 1 次；caption 只出现在第三个附件。 |
| `AT-ATT-002` | `BR-ATT-004` | 附件全部成功后名片调用恰好 1 次；附件存在永久失败时名片不发送。 |
| `AT-ATT-003` | `BR-ATT-004` | 空正文、空附件、至少一张名片通过内容校验。 |
| `AT-ATT-004` | `BR-ATT-005` | 非 direct 附件路径没有包在目标级整体重试循环中。 |
| `AT-JOB-001` | `BR-JOB-001/002` | `running` 初始化异常判定为终态失败；`queued/scheduled` 初始化异常保持可恢复。 |
| `AT-DRAFT-001` | `BR-DRAFT-001/002` | 编辑器 owner 与当前账号不一致时拒绝创建 Job；新会话和成功创建后清空 Excel/名片草稿。 |
| `AT-TARGET-001` | `BR-TARGET-001` | 相同 chatId 的重复目标只保留第一次出现的名称与顺序。 |

## 恢复与验证

- 代码回滚单位是本契约对应的修复提交；不回滚 #166 的账号级 Job 基础架构。
- 自动验证只使用 GitHub 托管 CI。不得启动本机 Geek self-hosted runner，也不得影响本机其他仓库的 CI。
- GitHub CI 通过只证明代码/contract 层；WA/TG/LINE 真实客户端附件回归仍是 Draft PR Ready 前的独立门禁。
