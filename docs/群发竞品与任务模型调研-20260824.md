# 群发竞品与任务模型调研 - 2026-08-24

> 本文补充 Issue #165 与 `docs/群发多账号并发补充.md`。目的不是复刻竞品界面，而是用成熟产品的任务模型验证极客群发的账号隔离、并发、定时和运行反馈设计。

## 调研对象

### SaleSmartly

官方群发能力明确支持：

- 多账号同步群发；
- WhatsApp App / WhatsApp API / Messenger / Telegram / Instagram / LINE / Email 等多个渠道；
- 受众筛选；
- 文本、图片、附件、视频、音频、变量；
- 发送间隔；
- 定时发送；
- 群发完成后查看计划发送人数、已发送人数、成功、失败和详情。

关键参考：

- https://www.salesmartly.com/features/broadcast-messages/
- https://help.salesmartly.com/docs/mass-message

对极客的意义：

1. 多账号并发不是特殊能力，而是成熟跨境客服/营销产品的正常工作方式；
2. 用户看到的是“计划 / 任务”，而不是一个占住页面的长时间发送弹窗；
3. 成功、失败、计划总数、发送详情应属于任务本身。

### AdsPower RPA / RPA Plus

AdsPower 与极客同样属于多账号/多环境桌面工具，它的任务模型更值得参考。

官方资料显示：

- 一个流程可以选择多个 profile 执行；
- 通过“任务线程数”控制并发，超出的 profile 进入队列；
- Task Log 区分 Waiting / Pending / Running / Complete / Error / Cancelled 等状态；
- RPA Plus 把“流程”和“任务”分开；
- 任务保存流程、执行 profile 和运行设置；
- 运行结果按任务 / 批次查看，并能继续下钻到 profile；
- 运行中的 profile 可以停止，失败任务可以重跑。

关键参考：

- https://www.adspower.com/rpa
- https://www.adspower.com/blog/adspower-rpa-plus
- https://rpa-doc-en.adspower.com/docs/Task
- https://rpa-doc-en.adspower.com/docs/quLqLP

对极客的意义：

1. 不应该有一个窗口级 `broadcastRunning`；应由 Job Manager 管理多个账号 Job；
2. 不同账号可以并发，同账号仍串行；
3. 同账号发生任务碰撞时，应进入明确的 queued 状态，而不是静默失败或串到当前任务；
4. 任务状态应该是一等数据，而不是从 DOM 文案反推；
5. “运行任务”与“编辑草稿”必须分离。

### respond.io

respond.io 的 Broadcasts 模块把群发当作独立对象管理，列表中有 Draft / Completed 等状态，并展示计划时间、名称、标签、Channel 和受众规模。创建群发时再进入 builder，选择 Segment、Channel、消息内容和发送方式。

关键参考：

- https://respond.io/help/broadcasts/sending-a-simple-broadcast
- https://respond.io/help/broadcasts-module/broadcasts-overview

对极客的意义：

1. Draft 是可编辑的；Job 是已经发布/启动的不可变执行快照；
2. 账号/渠道必须是任务配置的一部分；
3. 群发摘要应该在发送前就告诉用户“从哪里发、发给多少对象、何时发”。

### SleekFlow

SleekFlow 创建 Broadcast 时明确把时间拆成：

- Send now
- Schedule

同时指出 Scheduled Broadcast 的 audience 可能在实际发送时重新计算。

关键参考：

- https://help.sleekflow.io/running-broadcast-campaigns?kb_language=en_US

这提醒我们必须明确“定时任务受众是固定还是动态”。极客当前没有真正的动态 Audience/Segment 引擎，因此不能默默重新计算。

极客决定：**定时群发默认使用固定受众快照。**

用户点击创建定时任务时冻结 `targets[]`，UI 显示类似：

`已固定 52 个发送对象`

如果以后增加“动态标签受众”，必须作为单独模式明确告诉用户，而不是改变现有定时语义。

### Intercom Outbound

Intercom 明确区分 Fixed Audience 与 Dynamic Audience，并且消息进入 live 状态后，受众规则不再像草稿那样随意编辑。其 Outbound 列表也将 live / draft / paused / scheduled 作为明确状态。

关键参考：

- https://www.intercom.com/help/en/articles/3467924-dynamic-and-fixed-audiences
- https://www.intercom.com/help/en/articles/3292835-outbound-explained

对极客的意义：

1. 已经运行的 Job 不能继续被编辑器变量改变；
2. 定时任务受众语义必须清楚；
3. scheduled / running / paused / completed 等状态应该由任务模型直接表达。

## 调研后的极客目标模型

### 1. 三层对象，不再混在一起

#### BroadcastDraft

账号页面里正在编辑的草稿，可变：

- message
- selected targets
- files
- vcards
- tagAll
- exclusions
- interval
- schedule inputs

草稿属于当前 `accountId`，但没有发送副作用。

#### BroadcastJob

用户点击立即发送，或定时任务到点后创建的执行快照。创建后发送参数不可被 UI 改写：

- jobId
- accountId
- accountName
- platform family
- partition
- guestId / WebView reference
- targets snapshot
- message snapshot
- attachments snapshot/reference
- vcards snapshot
- tagAll snapshot
- intervalMin / intervalMax
- createdAt / startedAt / finishedAt
- state
- current / total / ok / fail
- failed[] / failReasons[]
- pauseRequested / stopRequested

#### BroadcastJobManager

目标结构：

`broadcastJobs = Map<accountId, BroadcastJob>`

规则：

- 每个账号最多一个 active Job；
- A/B/C/D/E 不同账号可以同时 running；
- 暂停 A 不影响 B；
- 停止 B 不影响 A；
- 一个 Job 内 targets 继续顺序发送；
- 不为了吞吐修改现有间隔和发送安全校验。

## 2. 任务状态

建议统一状态：

- `scheduled`：等待计划时间；
- `queued`：已到时间，但同账号当前有活动 Job；
- `running`：执行中；
- `paused`：用户暂停；
- `stopping`：已请求停止，等待安全停在下一边界；
- `completed`：任务结束；
- `stopped`：用户停止后结束；
- `failed`：任务初始化级失败，未能正常进入逐目标执行。

“部分失败”不需要额外状态，可用 `completed + fail > 0` 表达。

## 3. 同账号碰撞策略

不同账号直接并发。

同账号只能一个 active Job，但定时任务不能因为撞上正在运行的 Job 就丢掉。

调研 AdsPower 的队列模型后，极客决定：

- 手工群发：当前账号已有 active Job 时，默认聚焦当前任务，不重新初始化编辑器；
- 定时群发：到点时若同账号已有 active Job，进入 `queued`；
- active Job 完成/停止后，自动启动该账号最早到期的 queued Job；
- queued Job 在所属账号页任务区域显示“等待上一任务完成”；
- 不同账号的 queued/running 状态互不影响。

这比“到点失败”更符合用户预期，同时仍保持同账号单发送队列。

## 4. UI：任务条不跟账号跑，但账号本身需要状态提示

右上角任务条仍遵守：

`activeId === job.accountId`

也就是 A 的任务条永远只出现在 A 页面。

但用户切到 B 后，需要知道 A 仍在后台工作。为了不把 A 的任务条带到 B，建议在左侧账号 A 项目上显示很轻的账号级状态点：

- 运行中：小型进度/发送中标记；
- 暂停：暂停标记；
- 完成：一次性完成点；
- 失败：红色小点。

状态标记附着在账号 A 本身，不是全局 Toast，也不会遮挡聊天页面。

## 5. 发送前摘要

成熟 Broadcast Builder 普遍在发布前让用户明确受众、渠道和时间。

极客发送区应至少显示：

`账号 A · 52 个聊天 · 2 个附件 · 间隔 5–10 秒`

定时时再加：

`8月24日 18:30 · 已固定 52 个对象`

用户不需要再点一个二次确认弹窗。

## 6. 定时任务必须真正独立于当前页面

目标 registry：

`scheduleTaskTimersByAccount = Map<accountId, Map<taskId, timer>>`

切换账号只刷新当前编辑 UI，不能清理其他账号 timers。

schedule task 本身必须保存：

- taskId
- accountId
- scheduledAt
- targets snapshot
- message/content snapshot
- send options
- interval
- attachment references

到点后由 scheduler 创建对应账号的 BroadcastJob，而不是打开/改写群发编辑器再调用发送函数。

## 7. 新发现：定时附件不能继续使用当前 6 小时临时 token

当前 `src/broadcast-files.cjs` 的 `tokenTtlMs` 为 6 小时，而且 registry 是主进程内存 Map。

因此：

- 6 小时后的定时发送附件 token 会过期；
- 应用重启后 registry 也不存在；
- 所以当前临时 file token 只能用于即时/短时间运行任务，不能作为持久定时附件引用。

正确方向不是把 renderer 暴露回真实路径，也不是无限延长临时 token。

应新增主进程持久的 `ScheduledBroadcastAttachmentStore`（名称可调整）：

- renderer 只持有 opaque attachment/job id；
- 主进程保存真实 canonical path；
- 路径数据不通过 `accountData.getAll` 暴露给 renderer；
- 数据需与 accountId / taskId 绑定；
- 到点发送前重新 `stat` 校验 size/mtime；
- 文件被移动、修改或删除时 fail-closed，任务记录明确失败原因；
- 应用重启后仍可恢复；
- 任务完成/删除后清理持久引用。

该安全边界实现可能需要单独 Issue/PR，但它是“定时附件真正可靠”的必要条件，不能用 UI 文案掩盖。

## 8. 不照搬竞品的地方

不做一个新的重型“营销后台”替代现有聊天工作区。

极客的优势仍然是账号页面即工作现场，所以：

- 编辑群发可以继续用当前轻量弹窗；
- 开始后立刻回聊天页面；
- 当前账号右上角任务条反馈实时执行；
- 账号侧栏提供跨账号的轻量状态感知；
- 完整任务历史/洞察后续可以扩展，但不应该为了它阻塞当前聊天工作。

## 9. 由调研得到的新增验收

1. A/B/C/D/E 不同账号可以同时运行群发；
2. 同账号 active Job 只有一个；
3. 定时任务与 active Job 撞车时进入 queued，不丢任务、不串任务；
4. Draft 的任何修改都不能改变已创建 Job；
5. 定时任务默认固定 targets，并明确显示固定数量；
6. 切换账号不清理其他账号 scheduler；
7. 左侧账号可以轻量看出哪个账号正在发送/暂停/失败，但右上角任务条不跨账号跟随；
8. 任务结果可直接得到 total/ok/fail，不从 DOM 文案反推；
9. 定时附件超过 6 小时、跨重启仍要有正确、安全的持久引用；
10. 所有现有 WA/TG/LINE transport、安全校验和附件 opaque boundary 不因并发而弱化。
