# HaloGPT 群发参考分析 - 2026-08-24

> 参考来源：`reference/halogpt-helloworld-source` 分支。
>
> 该分支 README 已明确说明：内容来自安装包解包/净化后的研究材料，并非上游原始 Git 工作树，且存在压缩、混淆和缺失。因此本文只把它作为“行为证据与架构参考”，不把它当作可以直接复制到生产代码的源码。

## 1. 结论先行

这份参考源码确实验证了用户提到的“多账户并发群发”。

它不是用一个窗口级 `running` 布尔值控制所有账号，而是把批量发送状态按 `appId` 记录，并且能够选择多个同平台账号，把一批号码拆分后交给多个账号各自的 WebView 执行。

这进一步证明极客当前把运行态放在：

- `broadcastRunning`
- `broadcastPaused`
- `broadcastStop`
- `broadcastCurrent`
- `broadcastOkCount`

等窗口级变量中，是群发架构本身需要修正，而不是 Electron/WebView 不支持多账户并发。

## 2. 参考源码中的账号模型

参考应用的 store 同时维护：

- `appList`
- `currentAppId`
- `currentApp`
- `currAccounts`
- `lazyList`
- `batSendStatus: {}`

其中 `batSendStatus` 不是单一布尔值，而是按账号 `appId` 写入状态。

接收到账号 WebView 的 `batSendStatus` 消息后，其逻辑等价于：

```text
batSendStatus[appId] = status
```

也就是说，是否参与批量发送是账号级数据。

这与极客目标模型：

```text
broadcastJobs = Map<accountId, BroadcastJob>
```

方向一致。

## 3. 真实存在的多账号群发

参考源码处理 `batSend` 时会：

1. 遍历全部账号；
2. 只选与当前账号同平台 `type` 的账号；
3. 只选 `batSendStatus[appId]` 已开启的账号；
4. 取得每个账号对应 WebView 的执行函数；
5. 根据参与账号数量拆分 `phones[]`；
6. 分别在各账号执行各自的 `g_mutilBatSend(...)`。

因此这里存在两层并发含义：

### A. 账号之间可以同时执行

这是极客本轮必须支持的：

- A 有自己的 Job；
- B 有自己的 Job；
- C 有自己的 Job；
- A/B/C 可以同时 running；
- 暂停 A 不影响 B/C。

### B. 一个群发活动可以拆给多个发送账号

参考应用还进一步支持：一批 `phones[]` 自动分片，由多个同平台账号共同消化。

例如：

```text
活动 X：300 个号码
  WhatsApp A -> 100
  WhatsApp B -> 100
  WhatsApp C -> 100
```

这和极客目前讨论的“不同账号各自独立群发 Job”不是同一个产品语义。

本轮不应偷偷改变极客已有群发语义。若未来需要，可以单独设计为明确的：

**联合账号群发 / 多账号分摊发送**

用户必须主动选择参与账号，系统再明确显示每个账号负责的数量。不能把这种分片行为作为普通群发的隐式默认值。

## 4. 执行上下文与当前页面分离

参考应用每个账号有独立 `appId` 和持久 partition：

```text
persist:webview-page-${appId}
```

账号 WebView 并不会因为 `currentAppId` 切换而变成另一个账号的执行上下文。

`currentAppId` 更接近“用户正在看哪个页面”，而不是“哪个账号允许后台工作”。

这直接验证极客本轮最重要的原则：

> `activeId` 只决定当前显示什么，不得决定已经创建的 BroadcastJob 由谁执行。

## 5. 账号级后台执行器

参考应用在一种 `gvBatSend` 路径中，会为明确的 `appId` 创建一个后台 WebView：

```text
bat-send-elm-${appId}
```

它继续使用这个账号自己的 partition，并关闭 background throttling，然后执行该账号的批量发送逻辑。

这说明其设计理念是：

**任务执行上下文属于账号，而不是属于当前可见页面。**

这一点值得吸收，但极客不需要照搬“再创建一套隐藏 WebView”。

极客现有多账号 WebView 已经常驻，优先方案应是：

- Job 创建时固定对应账号已有 WebView / guestId；
- 后台继续使用该 resident WebView；
- 切换可见账号不改变 Job 的 executor；
- 只有在现有 WebView 生命周期无法可靠支持后台执行时，才另行评估独立 executor。

不要为了模仿参考产品而平白增加第二套 WebView 生命周期。

## 6. 暂停 / 继续 / 停止也是账号级的

参考应用对后台群发控制时，会根据明确 `appId` 找到：

```text
#bat-send-elm-${appId}
```

然后：

- `stop`：只移除该账号的后台发送 WebView；
- pause/resume：只向该账号执行器发送 `g_batSendStatus(...)`。

因此它不存在“暂停 A 误伤 B”的窗口级控制语义。

极客应保持已经确定的目标接口：

```text
pauseBroadcastJob(accountId, jobId)
resumeBroadcastJob(accountId, jobId)
stopBroadcastJob(accountId, jobId)
```

不得继续由全局 `broadcastPaused / broadcastStop` 控制。

## 7. 进度回传也是账号定向的

参考应用后台执行器收到 `sendedIndex` 后，会把该账号的发送序号/结果回送到对应原账号页面，由原页面执行类似：

```text
g_renderBatSendLog(index, data)
```

这说明：

- executor 可以在后台；
- progress 是结构化事件；
- UI 是这个账号任务状态的消费者；
- 用户是否当前正在看该账号，不应影响执行或进度累计。

这对极客当前 WIP 有一个重要修正：

**最终版本不能继续通过观察 `#broadcast-progress-text`、`#bc-sent-count` 等 DOM 文案反推 Job 状态。**

正确方向应该是发送循环直接更新：

```text
job.current
job.ok
job.fail
job.nextSendAt
job.state
```

任务条再纯粹 render(job)。

DOM 只显示状态，不作为状态源。

## 8. 对极客可以直接吸收的原则

### 8.1 状态按账号键控

参考：`batSendStatus[appId]`

极客：`broadcastJobs.get(accountId)`

### 8.2 executor 明确属于账号

Job 必须冻结：

- accountId
- partition
- WebView / guestId
- platform family

执行循环不再通过 `activeId` 重新找账号。

### 8.3 控制命令必须带 owner

pause / resume / stop 必须定向到 accountId/jobId。

### 8.4 当前页面与后台执行解耦

用户切 A -> B，只改变当前可见页面和任务条，不改变 A 的 executor。

### 8.5 进度是数据，不是 DOM 文案

发送成功、失败、当前 index、等待时间、完成状态都由 Job 自己维护。

### 8.6 多账号并发是自然能力

只要去掉窗口级运行态，不同账号 WebView 本身就可以各自跑自己的串行发送循环。

## 9. 明确不照搬的实现

参考应用基于较老的 Electron 体系，其中后台 WebView 配置可见：

- `contextIsolation=no`
- `sandbox=false`
- 大量字符串形式 `executeJavaScript(...)`

这些只能说明其行为，不是极客应该复制的安全实现。

极客必须继续保持自己的安全约束：

- 不降低 WebView sandbox / contextIsolation / webSecurity；
- 不绕过 `GeekBroadcastSafety`；
- 不把真实附件路径暴露给 renderer；
- 不取消附件 opaque token / owner 校验；
- 不为并发放宽目标聊天与 composer 校验；
- 不因为参考应用能执行字符串 JS，就增加新的任意 JS IPC 面。

## 10. 关于“隐藏后台 WebView”的取舍

参考应用使用额外隐藏 WebView 有一个明显优点：发送时可以和用户当前可见聊天页面进一步隔离。

但它也会增加：

- 登录/session 生命周期复杂度；
- partition 同时被两个 WebView 使用的行为风险；
- 资源占用；
- 重载/登录失效/插件加载的同步问题；
- 新的安全攻击面。

极客现阶段应优先采用已有常驻账号 WebView 作为 executor。

如果真实客户端测试证明“用户在同一账号页面手工聊天会干扰正在运行的群发 executor”，再单独评估“账号级后台执行 WebView”。不能预先为了架构漂亮而复制。

## 11. 参考源码目前没有足够证据支持的内容

截至本轮已定位代码，可以确认：

- 账号级批量发送状态；
- 多同平台账号共同参与；
- recipient 分片；
- 每账号执行上下文；
- 每账号 pause/resume/stop；
- 每账号进度回传。

但目前没有找到足够可靠的证据证明这套参考应用还实现了：

- 持久化 scheduled queue；
- 跨重启恢复的群发 Job；
- 同账号多个群发任务排队；
- 定时附件持久化。

这些内容仍以我们自己的仓库事实和此前对 AdsPower/respond.io/SaleSmartly 等公开资料的调研结论为依据，不从混淆源码中臆测。

## 12. 对 Issue #165 的最终影响

参考源码进一步加强以下本轮验收条件：

1. `BroadcastJobManager` 必须以 `accountId` 为 key；
2. A/B/C/D/E 不同账号允许同时运行；
3. pause/stop/progress/history/failure 全部账号隔离；
4. `activeId` 只用于选择当前显示的账号任务条；
5. Job 状态由执行器直接写，不由 DOM observer 反推；
6. resident WebView 作为第一选择的账号 executor；
7. 参考源码的“单活动多账号分摊”记为未来可选能力，不混入普通群发；
8. 参考源码中的弱 sandbox / raw JS 注入不进入极客生产设计。

## 13. 可选后续产品：联合账号群发

如果未来需要把一批联系人更快地分摊给多个同平台账号，可以在 Job Manager 正确后增加一个更高层对象：

```text
BroadcastCampaign
  -> Account A Job
  -> Account B Job
  -> Account C Job
```

Campaign 负责：

- 用户选择哪些发送账号；
- targets 分片；
- 每个账号独立安全间隔；
- 汇总 total/ok/fail；
- 单个账号失败时其他账号如何处理。

这样既能获得参考应用的多账号分摊能力，又不会破坏极客“一个 Job 永远只属于一个账号”的核心不变量。
