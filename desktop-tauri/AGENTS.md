# Windows desktop foundation: local engineering rules

Read repository-root AGENTS.md, this file, ARCHITECTURE.md and UI-PARITY.md before changes.
This is a separate Windows/Rust/Tauri development line. Do not migrate real Electron
profiles, change the production version/release marker, merge the draft migration PR,
or publish a client as a side effect of foundation work. LINE is deliberately deferred.
Manual real-account acceptance belongs to the owner; it does not block automated work.

## Non-negotiable size and readability rule

Every handwritten source/config/test/script file in this foundation must be at most
**3000 physical lines**, including comments and blank lines. Start reviewing a split
at 500 lines. This is a ceiling per file, not a target and not a 3000-line project limit.
Do not minify, join statements, hide code in strings, invent generated-code exclusions,
or raise the limit to pass the gate. Split by cohesive responsibility, not arbitrary
numbered chunks. The small Tauri workflow follows the same ceiling.

The genuine generated Cargo.lock is dependency data, not handwritten code. Tauri's
untracked target/, gen/ and permissions/autogenerated/ outputs and node_modules are
not handwritten source. Do not commit those directories or use them to hide code.

## Preserve the existing product UI

Tauri replaces the desktop runtime, not the product design. Build from the original
`ui/index.html`, presentation styles and icons through `scripts/prepare-frontend.cjs`.
Do not restore the rejected sidebar-form prototype or introduce a parallel design.
Original Electron scripts are not loaded in Tauri. Keep unsupported controls in their
original locations with explicit unavailable state; never fake successful behavior.
UI geometry changes and modals must synchronize the native guest before becoming
interactive. Keep account identity independent from selection and visibility.

## Architecture and ownership

- domain: pure account/schema/navigation rules and stable typed error codes.
- application: sole account transaction and workspace/lifecycle owners; native and
  persistence effects are ports. No Tauri, filesystem, process or network implementation.
- infrastructure: DPAPI, file locking, atomic repository, profile paths and build catalog.
- desktop: authorized IPC ingress, WebView2 host, native layout and tray adapters.
- bootstrap/main: composition only. No business policy or feature accumulation.
- frontend: app composition -> controller -> view/model; only api/desktop.mjs touches IPC.
- contracts/commands.json: command inventory. Registration, permissions, wrappers and
  AppManifest must agree. Never authorize the entire main window or remote guests.

Keep authoritative account metadata private. A candidate must persist successfully
before memory/UI/tray preferences become authoritative. A side effect is not a durable
transaction. Account UUID, profile and native guest binding never follow UI focus.
Archive is one Rust-owned operation; do not move multi-step business policy into JS.

Blocking I/O/native operations run through the common blocking executor. UI-thread
callbacks must not wait on the workspace mutex. Do not hold that mutex for network,
translation, attachment upload, send or broadcast jobs. Each future feature gets an
explicit owner, cancellation semantics and bounded concurrency before integration.

Remote pages receive no local file/shell/eval/secret APIs. Keep secure WebView defaults,
account-owned navigation, popup/download/permission denial until deliberately adapted.
Only the reviewed DPAPI module contains unsafe FFI. No plaintext secret fallback,
private-path/native-error echo, real-chat logging, token extraction or data reset.

## Required development checks

Run `node desktop-tauri/scripts/run-tests.cjs` from the repository root. It first runs
the architecture/line-limit/IPC checks, then discovers every *.test.mjs test. Mutation
tests must prove that gates reject violations; do not just assert today's file count.

On Windows run Cargo fmt --check, Cargo clippy with -D warnings, Cargo test and the
standalone release EXE build. Keep exact-source CI evidence separate from synthetic
UI tests, real WebView2 runtime checks, manual real-account acceptance and releases.
Commit actual Cargo-generated dependency locks and use --locked once the lock is
captured. Do not hand-author lock checksums or call an unlocked build reproducible.

For every feature change: identify its owner, change the smallest complete path,
exercise failure/rollback and cross-account isolation, review the diff, commit to the
migration branch, and inspect exact-head CI. Record current progress in the focused
PR rather than turning architecture documents into a second live task queue.
